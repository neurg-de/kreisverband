## Root cause and inspected WordPress behavior

The previous AJAX media restriction used authorship and bypassed filtering for edit_others_posts, while content uses gk_zuordnung and the legacy migration guessed scope from authors. There was no taxonomy object-capability guard, so authors could still directly edit their own foreign-scope items. Existing gk_ovautor lacked delete_published_posts and office lacked delete_others_posts/pages, while delete_post cannot distinguish permanent deletion from restore.

Inspected WordPress 6.9 core in the test container: wp_delete_post, wp_delete_attachment, wp_trash_post, wp_untrash_post, wp-admin/post.php, media list table, REST posts controller and taxonomy relationship APIs. wp_trash_post does not itself authorize the caller; delete_post is also used by restore; attachments emit add_attachment/edit_attachment instead of save_post; MEDIA_TRASH defaults off; wp_set_object_terms omits old_tt_ids when appending; get_post_status resolves attachment inherit to parent status/publish. Guards and tests account for these behaviors. Official references: https://developer.wordpress.org/reference/functions/wp_delete_post/ and https://developer.wordpress.org/reference/functions/wp_delete_attachment/ .

## Handbook / migration instructions

1. Keep geschaeftsstelle as **KV-Autor (mit OV-Zugang)**, never administrator. The update adjusts theme role capabilities only and preserves all account roles.
2. Matrix: KV-Autor works on own KV posts/pages/persons/events; KV-Autor mit OV-Zugang works across authors and all KV/OV areas; OV-Admin works across authors inside own OV on posts/pages/persons/events; OV-Autor works on own posts/persons/events inside own OV and cannot create pages. Media selection is shared within allowed scope even across authors. All four can upload and safely trash authorized content, none can permanently delete. OV-Admin retains own Verband access but **global menus/Customizer/setup are administrator work** after removal of edit_theme_options.
3. OV responsibility continues the established username == gk_zuordnung slug convention. No new user-meta mapping was introduced. Missing OV assignment fails closed and must be corrected by administration.
4. WordPress trash remains subject to the configured automatic retention period. Restore editorial content as draft and review before publishing. Attachments restore to inherit so they reappear in the library. Use Media list view > Papierkorb, and the notice link **Medien-Papierkorb öffnen** for restore. If trash is disabled site-wide, permanent deletion remains blocked; administration must enable retention for usable trash.
5. Before migration, back up database and files and test in staging. The old content migration now excludes attachments (OV worker updated ortsverband.php); it must not be used to silently classify media.
6. Admin opens **Medien > Zuordnung prüfen**. The initial view changes nothing. Check existing assignment, actual uses, parent and author suggestion; shared images and conflicting evidence require manual judgment. Choose the intended KV/OV explicitly and click **Geprüfte Zuordnung übernehmen** for that one image. There is no automatic bulk rewrite.
7. Verify media picker/list visibility as KV, office and each relevant OV; verify existing frontend featured images. Unassigned or multiply assigned legacy media is deliberately hidden from scope-limited pickers until reviewed, while broad office/admin access and existing rendered files remain intact.
8. To undo a migration, use **Letzte Zuordnung rückgängig machen** on that image. The stored before/after snapshot in `_gk_media_scope_rollback` restores the original assignment, including no assignment or multiple assignments. If the assignment changed subsequently or original terms were deleted, rollback refuses to overwrite; administrator investigates using the backup. A second migration of the same image requires first resolving its existing rollback snapshot; this intentionally prevents overwriting the only rollback history.
9. Theme rollback alone does not undo media assignments; use reviewed per-item rollback or the tested database backup. No files are renamed or deleted; attachment IDs, thumbnail metadata and URLs are unchanged by migration.
